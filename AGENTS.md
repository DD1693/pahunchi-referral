## Architecture rules
- Small AI = supplied `src/lib/sahaay/sahaay_classifier.js` + bundled `sahaay_model_v0.1.json`, used unmodified via `src/lib/sahaay/index.ts`; never substitute, rewrite, or fetch the model — it is the product's on-device AI.
- All data is local (IndexedDB via `src/lib/store.ts`); no database, auth, or sync backend — offline-first is a core requirement. The only server code is the optional passcode-gated "Talk to Pahunchi" connected demo (`src/routes/api/public/voice.ts` → `src/lib/voice/voice.server.ts`: ElevenLabs STT → Claude tool-forced extraction → in-code quote/enum validation); the core app must never depend on it.
- Service worker is generated by workbox-build in a custom plugin in `vite.config.ts` (vite-plugin-pwa skips SW generation under TanStack Start's multi-environment build); `src/lib/sw-register.ts` is the only registrar and pre-warms page shells into the `pahunchi-pages` cache.
- Shared component styles are Tailwind `@utility` classes in `src/styles.css` (Tailwind v4 cannot @apply plain classes).
- Referral detail uses `/referral?id=` (search param) so one cached page shell serves every record offline.
- Referral codes (`PH-XXXX`) are generated/backfilled in `src/lib/store.ts`; arrivals are a non-exclusive `arrivals[]` list; SMS follow-up is a `smsEvents[]` thread (transport simulated, parsing deterministic in `src/lib/sms.ts`); (patient-reported and facility-verified) also mirrored in history, so new arrival sources plug in without schema changes.
- Voice/IVR follow-up is simulated (`src/lib/ivr.ts`, `ivrEvents[]`); keypad 1 adds the shared patient_reported_arrival with `source: "ivr"`, at most one patient_reported_arrival per referral across channels; SMS/IVR arrival prompts are hidden once any arrival exists.
- Facility finder (`src/lib/facilities/*`, `FacilityFinder`) is a deterministic filter/sort over bundled illustrative synthetic data — never AI and never the barrier classifier; worker-chosen result is stored as optional `facilityRef` while `destination` stays a string, and practical constraints never enter `confirmedBarriers`.
- UI language (English | हिन्दी) comes from one dictionary in `src/lib/i18n.tsx` (`useT`); never fork workflows per language, and stored data is never translated.
- Facility type is a category id (`FACILITY_TYPES` in `src/lib/facilities/data.ts`) saved as `facilityType`; locked when chosen via the finder, manual selector otherwise; context only, never a ranking input.
- Journeys: `journeyId` (PJ-XXXX, generated/backfilled in `src/lib/store.ts`) groups referral legs; onward referrals use `/new?onward=<id>` and set `parentReferralId`/`origin`; `referralOutcome` is operational and separate from follow-up `outcome`.
- Arrival evidence has three non-exclusive sources (patient-reported, facility-verified, worker_confirmed_arrival); `needsAttention()` in `src/lib/followup.ts` groups operational follow-up, never by medical risk.
- Basic Phone Access (`/basic-phone`) is a simulated SMS menu (create/check/confirm arrival) that reuses `saveReferral`, `findFacilities`, `findByCode` and `confirmWorkerArrival` — never a parallel store; it and sync (`/sync`) make no network requests.
